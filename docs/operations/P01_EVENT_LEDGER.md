# P01-T09 — native privacy-scoped change event ledger

**Status:** IN_PROGRESS; original Windows CI #44987500956 failed only the concurrent first-opener fixture (30 passed, 1 failed). A process-local native bootstrap mutex and a simultaneous first-open regression test have been added; **new Windows CI pending**. This is a P01 native-only durability foundation, **NOT a released changelog**, GitHub issue publisher or user-facing What's New feed.

The Tauri native startup hook opens a separate `data/change-events-v1.sqlite` within the OS-resolved `com.zynoa.desktop` local app-data root. The existing SQLite WAL vault remains unchanged. The ledger itself uses SQLite WAL, FULL synchronous writes, an immediate write transaction, unique event IDs/idempotency keys, per-stream monotonic sequence and SQL triggers rejecting UPDATE and DELETE. Only a successful commit returns an event sequence acknowledgement; duplicate events fail instead of claiming success.

Events have compile-time allowlisted change/issue/test/docs categories, system/worker/CI origins, M01/M16/M17/M18/M23/M24/M26 modules, developer/private visibility and bounded ASCII identifiers. No arbitrary user text, message contents, full file paths, tokens or exception text can enter an event request. A native read method requires an explicit audience and hard 100-row maximum. The WebView has **zero** event commands or read capabilities. Production event ingress, full JSON envelope, signed-release truth and user-facing permissions remain unimplemented.

**Recovery:** reopening an existing v1 database runs `PRAGMA integrity_check` and schema presence validation. Existing corrupt or unknown-version stores are rejected without deletion or silent repair; linked/irregular database and SQLite sidecar occupants are denied. Rust fixtures cover restart replay, duplicated keys, per-stream sequence, private/developer isolation, SQLite-trigger mutation denial, parallel WAL writers, corrupt-source preservation and symlink handling. Windows real desktop smoke must prove the database exists outside the executable, schema v1, WAL mode and empty initial event set.

**Unfinished M26/UI gates:** sanitized idempotent issue bridge, ACL for frontend read APIs, encryption-at-rest policy, event archive/retention, privacy review and consent, release-manifest verification, Help/Wiki/screenshots, update feed and signed installer. There is **no remote event delivery**; an event is never considered a published release because this DB contains it. Do not mark T09 DONE before Windows/Governance verification.

**Concurrent first-open recovery:** SQLite transactions already serialize event append and stream sequence allocation, but two in-process native callers could concurrently observe a first-created DB file before its schema initialization finished. A narrow fail-closed process-local initialization mutex now surrounds full open/schema verification; concurrent steady-state event appends still use SQLite WAL and IMMEDIATE transactions. An eight-thread barrier fixture covers first-open, sequence continuity, restart replay, and no false acknowledgement. Cross-process first-initialization has not been independently demonstrated; the desktop already enforces a single native diagnostics writer on Windows. No forced database rewrite or deletion is performed.
