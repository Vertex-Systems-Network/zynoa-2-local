## Objective and outcome

Repository-aware professional coding with plans, editor, Git, terminal, tests and PRs. Product capability groups: projects; editor; diff; terminal; Git; tests; code agent. Main screens: File Explorer, Code Editor, Terminal, Git Diff, Test Explorer.

### Boundaries and dependencies

The module must be independently testable behind a typed adapter and feature flag. Dependencies on shared desktop kernel, project state, policy gateway, event bus and help router are explicit. It must not bypass another module's owner boundary or store uncontrolled copies of sensitive data. For P04, only the sub-scope in its phase contract is allowed. Errors and telemetry always use the diagnostics contract, not ad-hoc console output.

## Pre-development research and decision gate

Check active phase + branch lease, architecture decision records, tool versions/licensing, requirement IDs, threat boundary, data schema, UX options bank, tests planned before implementation and local baseline warnings. Review competing UX patterns and at least two implementation approaches, or explicitly record why only one exists. Record time/version/licensing and offline behavior of each candidate. The decision record must show evidence and the rejected alternatives. Verify any new dependencies, transitive licenses, compatibility and updater impact.

## Domain entities and interface boundaries

Proposed entities include `M04State`, `M04Settings`, `M04Command`, `M04Event`, `M04Artifact`, `M04IssueContext`, `M04HelpTopic` and versioned `<M04Event>` envelopes. The implementation must define Rust/TypeScript (or selected runtime) schema pairs with explicit version, correlation ID, user-visible state, idempotency identifier, validation errors and stable contract tests. Persist only data required for recoverable user value; default to local storage. Domain-specific services: Repo snapshot; worktrees; sandbox tool broker; test runner.

## Event and data-flow contract

1. A user gesture, file event, model response or authorized background trigger generates a typed command.
2. Command validates schema, workspace/project context, capability scopes and module lifecycle state.
3. Execution occurs in a supervised worker/service with resource limits and cancellation semantics.
4. Every observable transition is persisted or linked by stable job/trace identifiers before notifying UI.
5. UI subscribes to bounded events and renders the real source of truth, never invented progress.
6. Errors are normalized, shown with meaningful recovery and passed to local incident classifier.
7. Success is verified against deterministic outcomes, with artifact references and undo/rollback semantics where applicable.

**Event vocabulary:** code.plan.created, code.patch.applied, test.result, git.pr.updated. Define event ordering, replay, debounce, cancellation and backward-compatible payload schema.

## Failure taxonomy and automatic incident behavior

Classify: invalid input, access denied, dependency missing, runtime unavailable, provider offline, GPU memory exhaustion, state conflict, corruption, stale cache, migration mismatch, unhandled exception and performance budget regression. Errors must have stable codes, user-facing remediation and safe diagnostic envelope. Crash/warning fingerprint goes to M18 local spool; permitted developer errors automatically create/update GitHub issues, and user reports follow remote-reporting privacy policy. Avoid exception storms by grouping and suppressing duplicates, not hiding distinct systemic failures.

## Performance, correctness and test strategy

**Measurements:** Task solve rate; test pass; rollback success. Record baseline on reference machines and a target budget per UX path after measurement. Automated coverage: contract/schema tests, unit, property-based where applicable, integration, offline/failure injection, accessibility, real UI screenshot regression, crash recovery, security boundaries, documentation link checks and E2E. Check every option from table above, plus one realistic multi-step end-user scenario. Add tests for invalid values, cancellation, rapid repeated clicks, stale state, mixed case paths, restarted service and interrupted persistence.

## Security and privacy

Least-privileged scoped inputs/outputs; sanitize all imported material; no secret output or unapproved remote payload; separate developer diagnostics from end-user reporting; preserve exact source provenance where applicable; record permissions and denial reasons. Untrusted external text cannot become policy or executable commands. The module's audit events include decision and effective authority scope without logging personal content.
